# Agent Note: 损坏的 WhatsApp 凭据文件会中止连接

Status: implemented

[English](2026-08-21-whatsapp-damaged-auth-state.md) | 中文

## Problem

一个已配对账号不再恢复。provider 完成连接、报告 `pairing` 并打印二维码 —— 与首次运行完全一样。auth 目录除一处外完好无损：`creds.json` 为 0 字节。

Baileys 的 `useMultiFileAuthState` 以按路径互斥量串行化写入，但该互斥量仅限单进程，而写入本身是普通的 `writeFile`，它会先截断再写。进程在写入中途被杀死、或两个进程共用同一目录，都会留下被截断的文件。其读取方捕获解析失败并返回 `null`，而调用方对 `null` 的回应是 `initAuthCreds()` —— 一个新身份。

于是这一故障表现为一个全新的二维码。操作者扫码、得到可用的连接，却永远不会知道先前那台设备已成为账号已链接设备列表中的孤儿，也不会知道与旧身份绑定的会话密钥已经消失。除了把一个目录交给 Baileys 之外，harness 在其中没有任何参与 —— 这正是 harness 毫无察觉的原因。

## Decision

provider 在打开 socket 之前读取 `creds.json`，当该文件存在却无法解析时拒绝连接，报告 `WHATSAPP_AUTH_STATE_DAMAGED` 并指明该文件。文件不存在即视为首次运行并正常连接，因此配对流程不受影响。

这并不修复任何东西。它把一个静默且具破坏性的结果 —— 配对被丢弃，却以一次例行扫码的面貌出现 —— 转换为操作者可以据以行动的显式失败，这正是本仓库"配置错误应在最早可解析处失败，而非被跳过"的规则。

## Alternatives considered

**用一个原子写入的 auth store 替换 `useMultiFileAuthState`。** 这才是真正的修复：写入临时文件后重命名，使写入撕裂根本不可能发生，而不只是被报告出来。目前拒绝，因为这意味着要接管整个 `AuthenticationState` 表面 —— 凭据序列化、Signal 密钥存储，以及它们的 `BufferJSON` 编码 —— 去对抗一个不断变化的非官方协议，只为替换一个"在单进程独占该目录时工作正常"的依赖。该情形足够罕见，而如今又足够显式，权衡因此偏向检测。

**对 `authDir` 加建议锁，使第二个进程在启动时失败。** 这针对的是原因而非症状，并且还能真正修复已记录的"每个 `authDir` 只允许一个进程"这一限制。这里是推迟而非拒绝：锁需要陈旧持有者检测，否则会让操作者在一次崩溃之后再也无法启动；而要在每个受支持平台上把这件事做对，等于用一次罕见的静默丢失换来一次常见的显式失败。

**自动删除损坏文件并重新配对以完成恢复。** 这正是 Baileys 已经在做的，也正是本次要修复的行为。把它改为有意为之并不会更好：操作者依然静默丢失一台已链接设备，而现在还由 harness 来承担"丢弃自己读不懂的凭据"这一决定。

## Consequences

恢复需手动进行：删除该目录并重新配对。这一点与该限制并列写在 provider README 中，因为一个不写明补救方式的 fail-closed 错误只是把困惑挪了个位置。

provider 现在会在委托给 Baileys 之前从磁盘读取，因此它的测试覆盖一个真实的临时目录，而不再只有 socket 替身。双进程情形仍未被强制约束且已记录在案；本笔记正是"锁在到来时应加在目录上、而非环绕写入"的理由。
