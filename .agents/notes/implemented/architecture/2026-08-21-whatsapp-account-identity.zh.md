# Agent Note：账号 id 指明账号，而缺席不是占位值

Status: implemented

[English](2026-08-21-whatsapp-account-identity.md) | 中文

## 问题

`WhatsAppStatus` 的 `online` 分支携带 `accountId: string`，其值来自 Baileys 的 `socket.user?.id ?? 'unknown'`。这两半都是错的。

Baileys 上报的是所**链接设备**的地址，而不是账号：`554799229855:12@s.whatsapp.net`，其中 `:12` 是设备序号。同一账号再次配对会得到不同的 id，因此任何以它作为身份键的东西，在每次重新配对之后都会看到一个"新账号"。一次线上运行暴露了这个后缀。

回退值更糟。`'unknown'` 不是一个账号，而 `sameStatus` 正是比较 `accountId` 来判断状态是否变化 —— 于是两个真正不同、且都未具名的账号会比较为相等，第二次转换被当作重复而被抑制。运行路径里隐藏的 `?? default` 也恰恰是本仓库禁止的模式。

当时还没有任何消费者读取该字段：渲染它的 Web 面板正在编写，这是修正它将要展示之值的最省力时刻。

## 决策

去掉设备后缀，使 `accountId` 指明账号，并在重新配对前后保持稳定。

`accountId` 变为可选。若某次连接的地址库方并未上报，该字段保持缺席，消费者应陈述这一缺席，而不是替换成别的东西。这正是 seam 对尚未解析出显示名的对话已经采用的规则。

同一批改动中，seam 把 `pairing` 负载记为一份凭据。它是一个二维码，扫描者会链接一台拥有账号完全访问权的设备，因此其敏感程度高于消费者小心对待的消息正文；展示或转发它的界面，就是在选择谁能看到它。

## 考虑过的替代方案

**在每个消费者里各自去掉后缀。** 每个消费者都要重复同样的解析，而 seam 仍旧把一个设备 id 记作账号 id。对 WhatsApp 地址空间的判定属于 provider，理由与对话类型归属 provider 完全相同。

**保持 `accountId` 必填，并在库方未上报地址时断开连接。** 该连接完全可用 —— 能发送、能读取、能标记已读 —— 因此为一个展示字段而让它失败，是用一个可用的账号去换一项装饰性保证，而且重连预算会白白耗在一个重试无法改变的条件上。

**保留 `'unknown'`，只是把它写进文档。** 文档到不了 `sameStatus`，后者仍会把两个未具名账号视为同一个未变化的状态。缺陷在于占位值会比较为相等，而不在于读者不知情。

## 后果

消费者必须处理缺席的 `accountId`。这在渲染器里只是一个分支，换来的是一个从不撒谎的字段：有值即有账号，缺席即 provider 无法为其命名。

对未具名连接而言，状态去重现在是正确的，因为缺席不会像共享占位值那样彼此碰撞。
