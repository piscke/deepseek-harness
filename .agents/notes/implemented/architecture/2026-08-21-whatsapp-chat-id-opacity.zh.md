# Agent Note：WhatsApp 对话 id 不透明；对话类型归 provider 所有

Status: implemented

[English](2026-08-21-whatsapp-chat-id-opacity.md) | 中文

## 问题

`WhatsAppChatId` 看起来像一个可解析的地址。构建 seam 期间观察到的每个对话 id 都以 `@s.whatsapp.net` 或 `@g.us` 结尾，而子系统文档写着"无法归类某个对话的 provider 必须失败，而不是猜测"，这读起来像是在承诺这两个域就是全集。

它们不是。用这些工具驱动线上账号时，返回了一个地址为 `94257503293551@lid` 的具名对话 —— 这是 WhatsApp 正在为一对一聊天推行的链接身份地址空间 —— 与之并存的还有 `@newsletter` 与 `@broadcast`。

已经有消费者接受了这份邀请，按后缀重新推导对话类型，用于归类其对话索引尚未观察到的地址。结果是两个互相矛盾的工具：列出对话的工具返回了那个 `@lid` id，而读取对话的工具以 `"…@lid" is not a WhatsApp address` 拒绝了同一个 id。这正是文档所描述的顺利路径 —— 先列出，再读取 —— 而该错误针对一个账号确实持有对话的地址断言了一件不实的事。

## 决定

对话类型归 provider 所有，由它跟踪 WhatsApp 的地址空间；消费者读取 `WhatsAppChat.kind` 或 `WhatsAppMessage.chatKind`，而不是自行推导。

seam 新增 `resolveChat(chatId)`：只持有地址的消费者可直接取回该对话 —— 类型由 provider 判定，连接观察到时带上名称 —— 而不必解析。只有根本不指向任何对话的值（缺少用户或缺少域）才会被拒绝，并且由 provider 作出该判定，因为它才是知道"什么是地址"的那个包。

陌生域被归类为 `direct` 而非失败。seam README 声明对话 id 不透明且不得解析，子系统文档的分类规则改写为：该判定归 provider 所有，并以退化取代拒绝。一个测试把 `@lid` 钉在 `direct` 上，使这一优雅默认成为契约，而不是某个三元表达式的偶然结果。

索引成员资格同样不是前置条件。`fetchMessages` 对本连接从未观察过的地址返回空页，只拒绝根本不是地址的值，与 `resolveChat` 一致。账号本就可以向这样的对话发送消息并标记已读，因此单单拒绝剩下的这一个操作，会让热启动与打错号码无法区分。

## 考虑过的替代方案

**按旧规则在遇到无法识别的域时失败。** 这正是当初写下的规则，而线上账号说明了它为何错误：当 WhatsApp 把对话迁移到新的地址空间时，fail-closed 的 provider 会失明，而且从操作者一侧看是无声地、在推行途中失明，且没有任何可指认的坏输入。退化为 `direct` 只在 `@newsletter` 与 `@broadcast` 上是错的，其危害是把频道帖当作一对一消息；而拒绝，对新域上的每一个真实对话都是错的。

**枚举已知域并维持一个封闭集合 —— 即 allow-list。** 该集合不可知：这是一个未公开的协议，会在版本之间新增域。任何枚举都是"在 WhatsApp 发布之前正确"的列表，且其失败模式是拒绝有效地址，而不是给冷门地址贴错标签。

**按名字拒绝 `@newsletter` 与 `@broadcast` —— 即 deny-list。** 它不是上面那个 allow-list：deny-list 在 WhatsApp 新增域时是 fail-open 的，因而能安全退化，并且可以避免把频道帖标成一对一消息。它仍然不成立。`resolveChat` 在分类之前先查已观察索引，于是被观察过的频道解析为 `direct`，未被观察过的却抛错——而索引装的只是某一个进程恰好看到的内容，线上连接先返回了一个对话、随后是零个。若把 deny-list 放在索引之前检查，又会复现本笔记意在消除的矛盾：`listChats` 返回该 id，而 `resolveChat` 拒绝它。真实账号上也从未观察到任何频道地址，而新增一个 kind 要在两个包的每个 switch 里都付出一个 `case`。等真正出现一个再交付。

**在 provider 内把 `@lid` 归一化为电话号码地址，使消费者只看到一个域。** 很有吸引力，因为这能让地址空间保持单一。但 Baileys 并不总能把链接身份映射回电话号码，因此部分对话仍会以 `@lid` 出现，而信任该归一化的消费者恰恰会在映射失败的那些情形上出错。作为后续的信息增强值得做；作为保证则毫无用处。

**只禁止解析，却不提供替代。** 单说"对话 id 不透明"并不能让消费者据此行动：持有连接从未观察过的地址的工具，仍然需要该对话的类型来路由、需要名称来展示给操作者。seam 上的 `resolveChat` 才使这条禁令负担得起，因此它与禁令同批交付，而非事后补上。

**让 `fetchMessages` 在未观察过的对话上继续失败，因为空页与未知地址是两个不同的答案。** 它们确实是不同的答案，但索引成员资格从来不是二者之间的界线。索引装的是某一个进程恰好观察到的内容，而构建它的线上运行在一次连接时返回了一个对话、下一次却是零个，于是同一个 id 会因消息是否已经到达而时成时败。两种失败还都携带 `WHATSAPP_UNKNOWN_CHAT`，使消费者无法分辨“这个 id 是错的，停下”与“没有保留历史，但你仍可发送”。可寻址性把界线画在答案不会移动的地方。

## 后果

消费者无法从 id 得知对话类型，只能从 seam 得知。这正是目的：该分类如今只被陈述一次，且由那个在 WhatsApp 新增域时本来就必须改动的包来陈述。

seam 仍然无法把频道或广播列表与真人区分开，因为二者现在都以 `direct` 抵达。今天没有消费者需要区分它们，而诚实的修法是为它们增加一个 `kind` 成员，而不是在 seam 之上的某处做后缀检查。
