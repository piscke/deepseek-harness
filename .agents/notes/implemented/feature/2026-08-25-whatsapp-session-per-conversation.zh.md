# Agent Note: One WhatsApp session per conversation

Status: implemented

[English](2026-08-25-whatsapp-session-per-conversation.md) | 中文

## Problem

[WhatsApp 工作区](2026-08-22-whatsapp-workspace-and-tools.md)交付时带有三种路由形态，而示例组合用的是按种类归拢对话的那一种：一个 `Groups` 会话与一个 `Contacts` 会话。这种形态回答的是「谁在跟这个账号说话」，而不是这个子系统真正要回答的问题——长期读取某一个联系人的消息，并据此做点什么。

「按联系人的解读器」需要三样已交付的工作区没有给出的东西。

**一段对话的历史必须属于它自己。** 在共享会话下，某个联系人说过的话会成为其他每个联系人回合的上下文：模型被要求分清谁是谁，日志无法作为一个人的线程来读，压缩最终会为了给另一个人腾地方而丢掉这个人的事实。

**一段对话必须可辨认。** 按对话的形态用消息携带的名字为会话命名。只有私聊消息携带名字——群的主题是通过它自己的更新到达连接的——因此每个群会话在侧栏与会话列表里都以地址 `12036300000@g.us` 命名。

**回答一段对话的 agent 必须有工具。** `openSession` 创建会话时没有 `setup` 回调，而挂载预设名册只会经由 `setup` 发生。于是在 Web 组合中，每个 WhatsApp 会话都在没有预设的情况下运行：没有工具，没有提示词区段。agent 无法回答那条唤醒它的消息，而且没有任何地方说明这一点。

## Decision

一段对话就是一个会话，始终如此。工作区不再决定对话*如何*映射到会话；它决定自己回答*哪些*对话。

### `chats` 取代 `route`

`WhatsAppRouteMode`、常驻会话（`whatsapp-groups`、`whatsapp-contacts`、`whatsapp-conversations`）、它们的标题与 `openStandingSessions` 全部移除。取而代之的是 `chats`——`all`、`groups` 或 `contacts`——决定哪些对话打开会话，并在 `allowChatIds` 与 `denyChatIds` 之前判定，因此收窄范围不会被一条被遗忘的白名单条目打败。

会话标识不变：对话 id 的 `whatsapp-chat-<digest>`，也正是被移除的 `per-chat` 模式已经产生的那一个。运行过它的部署保留全部日志并继续恢复。

在被移除的形态下写出的会话既不迁移也不删除。它们仍挂载在工作区上、在侧栏中可读，新消息会在它们旁边打开按对话的会话。迁移将不得不臆造共享日志中每一个回合属于哪个联系人，而那个事实从未被记录。

### 对话的名字是 provider 拥有的事实

seam 上新增 `whatsapp/chat-named(chatId, name)`：连接得知或改变了某段对话的显示名。它之所以存在，是因为名字在消息流之外抵达——群的主题通过 `groups.update` 到达 Baileys，联系人的名字通过名册到达——因此一段对话在其首条消息被观察到时通常还没有名字，片刻之后才有。

Baileys provider 用一个监听器订阅六条名册流，并在某个群的首条消息不带名字时询问一次 `groupMetadata`。该查询绝不推迟那条消息：主题在查询落地时经由 `chat-named` 到达消费者。对同一个群的并发询问会合并为在途的那一次请求，查询失败会被警告并让该对话保持无名，而名字只在确实发生变化时才发布，因此重连后重新同步同一份名册是静默的。

名字保存在自己的索引中，与观察到的消息索引分开，因此得知一段对话叫什么绝不会凭空造出一个 `listChats` 随后会上报的对话。

工作区用解析出的名字为会话命名，其次是消息上的名字，最后是对话 id，并在 `chat-named` 到达时为已打开的会话改名。这正是首次接触时主题未知的群最终落在自己主题之下的方式，也是被改名的对话得以跟随的方式。

### 回答一段对话的 agent

`openSession` 现在会组合它所创建的 agent。`agentPreset` 指定新对话会话上挂载的预设；名册通过 `ctx.get('agentPresets')` 读取而非注入，因此没有名册的 headless 组合照常路由。被恢复的会话挂载其日志中记录的预设，而绝不是部署当前的那个：它的轮次是在它记录下来的那份组合下产生的。

新对话在 `ctx.agentDefaultModel.currentSelection()` 上打开。入站消息面前没有操作者来挑选模型，而没有模型创建出来的会话会在第一个轮次上以「has no provider/model」失败——本次变更中的快照最初复现的正是这一点。

该对话标识上已经发布的 agent——操作者正在 Web UI 中打开那段对话——会被直接投递，而不是在同一份日志上第二次恢复。路由器只释放自己打开的东西。

### 账号连接期间即可编辑路由选择

`chats`、`allowChatIds`、`denyChatIds` 与 `agentPreset` 同时是一个设置命名空间，WhatsApp 设置页在配对二维码旁边新增一张编辑范围的卡片。路由器按消息重读当前权威策略，因此变更对下一条消息即刻生效，无需重新加载；改动后的 `agentPreset` 对下一段打开的对话生效。

`directory` 与 `workspaceTitle` 留在该命名空间之外。它们决定工作区的身份，而身份在加载时固定，不能在已经挂载其上的会话之下改变。

该卡片位于普通设置平面，而不是[配对页面所需要的](2026-08-24-whatsapp-pairing-in-settings.md) loopback 通道：路由范围不是凭据。

## Alternatives considered

**在按对话的形态旁边保留 `category` 与 `single`。** 这是兼容的做法，也正是本次变更刻意不做的。三种形态意味着框架文本、标题、预设语义与每一张测试矩阵都要永远背负一个模式维度，只为了留住两种其全部价值在于减少会话数量的形态——而这个问题 `chats` 与 `denyChatIds` 直接解决，且不会把两个人的历史混进同一份日志。在发布前，正确的地基优先于兼容垫片。

**把常驻会话迁移为按对话的会话。** 之所以诱人，是因为用过 `category` 的部署会看到自己的历史停止增长。之所以否决，是因为映射并不存在：共享日志记录的是轮次，而不是每个轮次属于哪个联系人，按框架文本里的对话 id 切分则等于靠解析散文改写历史。旧会话保持可读，这是诚实的结局。

**在名字到来之前用地址为群会话命名，并就此不管。** 这是已交付的 `per-chat` 模式的做法。之所以否决，是因为地址恰恰是操作者认不出来的东西，而名字几秒之后就能拿到——跟随它的代价只是一个事件与一次条件性改名。

**在投递那条揭示该群的消息之前先解析群主题。** 更简单：标题在第一个回合就是对的。之所以否决，是因为这让一次网络调用成为投递消息的前置条件，于是缓慢或失败的查询会推迟甚至丢掉真实内容。命名是展示层的关注点，应当跟在消息之后。

**在工作区而非 provider 中推导名字。** 工作区可以调用 `resolveChat` 并缓存。之所以否决，是因为只有 provider 能看到名册流，而轮询 `resolveChat` 的消费者根本无从得知一次改名。命名属于连接所在之处。

**给工作区加上 `provider` 与 `model` 配置字段。** 曾为缺失的模型选择考虑过。之所以否决，是因为那会成为配置默认模型的第二处地方，并与 harness 其余部分读取的那一处发生漂移；`ctx.agentDefaultModel` 已经拥有「新建会话运行在什么之上」，并跟随用户存储的选择。

**在设置卡片中加入预设选择器。** 推迟而非否决：`agentPreset` 已在命名空间中且可编辑，但下拉框值得在真的有一个解读器预设可选之后再做。在那之前，卡片只会列出部署并非为此目的而组合的名册。

**在 WhatsApp 工作区内自动批准发送。** 不在本次范围内，并作为无人值守运行所缺的一块记录在案：`whatsapp_send_message` 仍然每次都询问操作者，因此解读器可以在无人参与下读取与记录，但不能在无人参与下回答。

## Consequences

全新部署的 WhatsApp 工作区起初是空的：在对话到来之前不存在任何会话。首次接触之后，侧栏会列出曾经回答过的每一段对话，因为会话与工作区的挂载是持久的。

会话无上限、无淘汰地打开，每段对话一个。`chats`、`allowChatIds` 与 `denyChatIds` 就是控制手段；上限或过期仍是推迟的工作。

框架文本没有变化，仍在每条消息上写出对话 id，尽管现在一个会话只服务一段对话。它是 `whatsapp_send_message` 所需要的值，而从这一轮里读出它，比指望模型从会话上下文中带着它走更可靠。

`whatsapp/chat-named` 是新的 seam 事件，因此每个展示对话名字的消费者都应当跟随它，而不是把首次读数当作最终结论。`WhatsAppChat.name` 已如此说明。

本文取代[工作区与工具那篇记录](2026-08-22-whatsapp-workspace-and-tools.md)中关于路由形态的部分；该记录中关于投递、框架文本、日志与面向模型工具的一切均未改变，仍然有效。

## Testing

包测试覆盖各类对话的范围过滤、允许/拒绝名单相对它的优先级、`fromMe`、用解析出的名字与消息上的名字命名、`chat-named` 触发的改名、创建时挂载的预设与恢复时日志中的预设、创建时传入的默认模型选择、投递进已发布的 agent，以及目录被移动时的失败。Baileys 的测试覆盖每一条名册流、按需的群查询、并发询问的合并，以及主题读不出来时的警告路径。设置卡片针对真实的命名空间 schema 与真实的 `settings.mutate` 线上调用受测。

一个无密钥快照重放已组装的应用：一条入站消息打开一个标题为 `Ana` 的会话，记录 `whatsapp/inbound`，把框架文本拼接进 agent 的收件箱，并完成该轮次。只用一段对话可以让请求序列保持确定；范围过滤与改名属于包级事实。

这里没有任何东西在真实 WhatsApp 账号上验证过。群命名尤其依赖 socket 替身：`groupMetadata` 与名册流都是经由端口演练的，从未针对 Baileys 本身。
