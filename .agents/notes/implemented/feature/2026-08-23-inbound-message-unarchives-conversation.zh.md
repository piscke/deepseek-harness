# Agent Note: An archived WhatsApp conversation unarchives when it speaks again

Status: implemented

[English](2026-08-23-inbound-message-unarchives-conversation.md) | 中文

## Problem

归档一个会话会让它那一行从所有分组视图中消失（[归档集合](2026-07-31-session-archive-global-set.md)），而没有任何东西会把 id 放回来。对于操作者已经处理完的会话，这是自洽的；对于一段 WhatsApp 对话则是错的：联系人继续写，router 继续投递，agent 继续作答，而这场往来发生在没有任何界面能抵达的地方——侧栏既没有归档视图也没有恢复操作。归档读起来像是把一段对话静音，行为上却是在对话仍在运行时删掉了它那一行。

## Decision

**一条被路由到某个会话的入站消息会在投递之前把该会话从注册表级全局归档集合中清除，于是重新开口的对话重新可见；注册表因此获得反向写入 `ctx.workspaceRegistry.unarchiveSession(id)`。**

- 注册表：`unarchiveSession` 与 `archiveSession` 并列走 `enqueueOperation`，因此它的“先检查后写入”不会与另一次归档变更交错。集合中不存在的 id 直接完成而不写入；而且与归档不同，会话不必仍然存在：集合条目比它的日志活得更久，拒绝移除只会留下一个任何界面都够不着的隐藏 id。因此 `WorkspaceUnknownSessionError` 仍然只属于归档一侧的失败。
- Router：`WhatsAppInboundRouter.accept` 在路由过滤与重放窗口之后才调用这次清除，因此被丢弃的消息绝不会让一段部署并不作答的对话重新浮现。成员判定同步读取 `archivedSessionIds`，因此未被归档的对话只多一次查找，不写入任何东西。
- 投递绝不等待它：那一行属于显示状态，写入失败只发出警告并让对话保持归档，消息无论如何都会到达模型。
- 线路层不需要任何新东西。`host/archived-sessions-changed` 已经通过比较 domain 全局状态在每次持久化变更后推送完整集合，客户端安装快照而不是合并增量，因此移除沿着新增早已使用的那条路径传播。

## Alternatives considered

**让归档保持永久，另外加一个手动取消归档的控件。** 作为本问题的答案被否决：恢复界面值得建，但它要求操作者先注意到一段被隐藏的对话——而看不见的对话恰恰是他们无法注意到的。两者彼此独立；手动控件仍然可以后续落地。

**让对话保持归档，用别的方式给出信号（角标、通知）。** 否决：这会在归档集合旁边发明第二套可见性概念，而它要指向的那一行正是被隐藏的那一行。

**在 `openSession` 内部取消归档，那里 Workspace 已经在记账该会话。** 否决：router 每个进程只打开一段对话一次，于是归档一段正在运行的对话将永远不会被撤销——而这正是常见情形，因为操作者归档的就是当下吵闹的那段。

**做成可配置（一个“保持对话归档”的策略字段）。** 暂时否决：真正能让一段对话停下来的部署控制项是 `denyChatIds`，它停止路由，而不是隐藏一场仍在进行的往来。等到有了手动恢复界面与之配对，策略字段才站得住。

**通用地清除集合，只要会话有任何活动。** 否决：没有哪个通用活动接缝拥有“用户正在被对话”这一含义，而后台 subagent 的一轮或一次维护写入都会让操作者刻意收起来的行重新浮现。WhatsApp 的入站流是一个人在说话，这才是这条规则成立的理由。

## Consequences

归档一段 WhatsApp 对话现在意味着“隐藏它，直到它重新要紧”，而不是“永久隐藏”；归档的含义在别处没有变化，没有入站流的会话在恢复界面出现之前仍然保持隐藏。由于写入不被等待，那一行可能在消息落地之后片刻才回来，而一次写入失败会让对话保持隐藏直到它的下一条消息。domain 测试钉住反向写入（持久性、席位位置的保持、重复调用不写入、会话已消失的 id），WhatsApp 组合测试钉住被路由路径的两个方向，包括注入介质失败时的“警告并照常投递”行为。
