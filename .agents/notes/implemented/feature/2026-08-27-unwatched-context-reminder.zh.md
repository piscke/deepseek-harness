# Agent Note: A session holding unread context announces itself in the sidebar

Status: implemented

[English](2026-08-27-unwatched-context-reminder.md) | 中文

## Problem

入站 WhatsApp 消息[作为待处理上下文等待](2026-08-26-whatsapp-inbound-as-pending-context.md)，而不是开启一个轮次。这在模型语义上是对的，作为到达信号却是错的：没有唤醒，就没有运行，于是侧边栏唯一的绿点——由 running→idle 边沿触发的完成提醒——永远不会亮起。操作者当前没有在看的会话收到消息后，它那一行与什么都没发生的行毫无区别。

被破坏的恰恰是操作者自己的用法。他们盯着一个会话，别人在另一个会话里写了消息，而到达的内容只有在他们猜对该打开哪一行之后才可读。对话记录会正确渲染等待中的消息；真正告诉他们哪份记录值得打开的界面，此前并不存在。

## Decision

`SessionManager` 在完成提醒之外，拥有第二个绿色提醒 `pendingContextNotifications`。它从权威的 `session/queue` 快照中读取：某一帧为非当前选中的会话携带了至少一条 `context` 放置项，就点亮提醒；不携带则熄灭。选中该会话即清除提醒，与选中清除完成提醒完全一致。

该位经 `SessionListEntry.pendingContext` 通过 `flattenLineage` 传入 `SessionSummary`、`SessionNode` 与 `SearchResultNode`，由 `sessionStatuses()` 呈现为标注 `status.newContext` 的 `done` 态圆点。它压过完成提醒——读者尚未看过的新材料，比一份他们已经读过的工作交代更重要——而待处理交互、自身活动与后代活动仍然压过它。

该提醒与生产者无关。宿主已为每一条注入消息解析出 `context` 放置，因此这个点报告的是"这里有你还没读的东西"，而不是"WhatsApp 来消息了"。审批通知与任务完成通知同样是注入的；它们会在运行中轮次的下一步边界被认领，而运行中的会话显示的是活动圆点，所以它们不会滞留成一个绿点。

## Why the queue snapshot rather than a projection

会话投影折叠持久日志，能跨重启存活，而队列快照不能：mux 基线只为拥有存活 agent 的会话重放 `session/queue`，因此冷会话中等待的上下文在它恢复之前不可见。

队列快照依然胜出，因为提醒必须与它所指向的界面一致。对话记录中的待处理行取自同一份快照，所以由它派生的圆点绝不会声称存在对话并未展示的材料。投影则必须从 `agent/inbox/spliced` 及每一次认领与取消中重新推导"仍在等待"，重复 `Inbox` 自己的裁决逻辑，并在两条推导发生漂移时与对话记录产生分歧。

## Alternatives considered

**只在上下文被某个轮次认领时清除圆点。** 更贴近"未读"：操作者打开并读过之后，材料其实仍在等待。已否决，因为这会让圆点成为队列的属性而非读者的属性，而侧边栏已经确立了相反的约定——完成提醒因"看过"而消费。一个看过之后仍不消失的圆点，操作者会学会无视它。

**改为在持久的 `whatsapp/inbound` 事件上点亮。** 直接且针对特定生产者。已否决，因为这会为宿主已经通用计算的事实，向侧边栏灌输某一个插件的词汇；而且持久记录说的是"消息到达过"，不是"它仍在等待"：已被认领或取消的消息会让圆点一直亮着。

**为等待中的上下文引入独立的圆点状态（新颜色）。** 已否决，属于无谓的词汇扩张。`StateDot` 有四种状态，而这里表达的正是完成提醒的同一主张——"这里有事情结束了，来看看"——所以它沿用同一种绿色，靠标签与悬浮卡片区分自身。

**在行内显示等待消息的条数。** 已否决：待处理上下文不设上限地累积，所以计数是无界的，而且并不能让操作者做出不同的动作。该行自己的悬浮卡片与对话记录承载内容。

## Testing

管理器测试针对队列帧钉住提醒的完整生命周期：为未被观看的会话点亮、绝不为被观看的会话或仅有 `queued`/`steering` 放置项时点亮、在不再携带该行的快照上熄灭、在 `session/subscribed` 上重建基线、随会话移除而丢弃、并在列表不再承载它时被清扫。行测试断言圆点、其标签，以及等待中的上下文压过完成提醒；树测试覆盖它向分组行、扁平行与搜索行的投影。

## Consequences

- 消息等待期间宿主重启过的会话，在其 agent 重新存活之前不显示圆点，因为 mux 基线只读取存活的 agent。持久记录与对话记录不受影响。
- 每一个注入上下文的生产者都继承该提醒。若未来某个生产者会例行地向空闲且未被观看的会话注入内容，它点亮的行会超出操作者的预期，届时需要的是它自己的放置类别，而不是在此处加一份抑制名单。
- 侧边栏现在有两个绿色提醒共用一种状态与一个槽位。`showsStatus()` 是决定圆点是否渲染的唯一谓词，因此第三个提醒只需在一处加入。
