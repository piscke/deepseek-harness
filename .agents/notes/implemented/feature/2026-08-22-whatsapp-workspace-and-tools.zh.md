# Agent Note: WhatsApp 工作区与面向模型的工具

Status: implemented

[English](2026-08-22-whatsapp-workspace-and-tools.md) | 中文

## 问题

[WhatsApp seam](../architecture/2026-08-21-baileys-runtime-specifier.md) 让 harness 拥有一个已认证账号：状态、对话、历史、发送，以及一个入站事件。但没有任何东西消费它。一个把 `whatsapp/message-received` 发进空房间的账号算不上助手——一个人的消息必须抵达模型，而模型需要一条回复的途径。

有两个问题必须一起回答，且都没有显而易见的默认答案。

**一段对话住在哪里？** harness 把工作组织为工作区中的会话，而工作区是一个目录。WhatsApp 没有仓库。每段对话一个会话、每类对话一个会话、以及全部合成一个，对不同账号都各有道理，而这个选择改变了模型一次能看到什么。

**入站消息何时抵达模型？** 消息在对方打字的任何时刻到达，包括某个轮次的中途。一个每条消息就开一轮的朴素监听器，要么在同一个会话上交错两个轮次，要么丢掉 agent 忙碌期间到达的一切。

## 决定

两个包，沿着仓库其余部分已有的那条线拆分：一个拥有持久状态与生命周期，另一个拥有模型读到的内容。

[`dsh-whatsapp-workspace`](../../../../packages/whatsapp/whatsapp-workspace) 确保一个目录存在（`directory`，默认 `~/.dsh/whatsapp`），通过 `ctx.workspaceRegistry.create()` 注册它，以等于该目录的 `cwd` 打开该路由的会话，通过 `ctx.sessionTitle.rename()` 固定它们的标题，并把入站消息作为后续轮次投递进去。

[`dsh-tool-whatsapp`](../../../../packages/whatsapp/tool-whatsapp) 注册 `whatsapp_list_chats`、`whatsapp_read_chat`、`whatsapp_mark_read` 与 `whatsapp_send_message`，每个都可独立关闭，其中发送由 `ctx.approval` 把关。

两者都是 `ctx.whatsapp` 的消费方，都不导入 provider。部署可以只取其一：没有工作区的工具是一种按需回答的无界面组合，`send: false` 的工作区则是只读分诊。

### 路由是 `Config`，因为没有哪一种形态适合所有账号

`route` 必填且没有默认值：`category`（一个 `Groups` 会话与一个 `Contacts` 会话）、`per-chat`（每段对话一个会话，首次接触时打开）或 `single`（全部合一）。`allowChatIds` 非空时即是穷尽列表，而 `denyChatIds` 优先于它。

形态选择没有存活下来：[每段对话一个会话](2026-08-25-whatsapp-session-per-conversation.md)移除了 `route`、`category` 与 `single`，代之以 `chats`——它决定*哪些*对话拥有自己的会话。以下关于过滤、框架文本、投递、日志与工具的一切均未改变。

有两条过滤源自 seam 自身的契约，不可配置。`fromMe` 消息永不路由——把部署自己的回答再送回去会用它自己的话唤醒 agent，而 seam 有意上报它们是因为状态显示需要。已投递过的消息 id 会被丢弃，因为 seam 的契约就是 provider 在重连后会重放历史。

路由不做第三种判断。一次真实配对中成批出现的、无人撰写的 `whatsapp/message-received` 帧曾让这种判断看起来必要，本里程碑也一度带着一份 WhatsApp 信封字段名的丢弃清单。那是错的：seam 上报的是最先被解码的那个信封键，而 WhatsApp 会在大多数群消息上附带 `senderKeyDistributionMessage`，因此一份宽到足以捕获信令的清单，会丢掉一张发到群里的照片——而且是悄无声息、日志中毫无痕迹。seam 现在保证入站事件是某个人发出的东西，修复属于那里，在信封仍然完整的地方。在此处复制这份判断，只会在两份清单发生漂移的那一刻重建同一个隐患，因此本包完全不检视任何 WhatsApp 字段名。

会话 id 是确定性的（`whatsapp-groups`、`whatsapp-contacts`、`whatsapp-conversations`、`whatsapp-chat-<digest>`），因此重启会恢复该对话，而不是另起一段平行的空会话。标题以 `user` 来源固定，这正是永久停止自动标题生成的手段；标题未变时会跳过重新固定，因此重启不追加任何内容。

### 每条消息都指名自己的对话

在 `category` 与 `single` 下，一个会话服务多段对话。因此对话身份是每条消息的一部分，而不是要求模型自己记住的上下文：

```text
WhatsApp message in group chat "Família" [chat_id: 12036300000@g.us]
From: Ana (5511999990000@s.whatsapp.net)
Sent: 2026-08-21T10:00:00.000Z

alguém pode buscar o bolo?
```

`[chat_id: …]` 的值正是 `whatsapp_send_message` 所要求的，因此回复给对的人是复制而非推断。这也是 `per-chat` 不采用更省的框架文本的原因：统一的框架意味着模型永远不会学到「对话头部有时会缺席」。

### 投递排队，永不打断

入站投递通过维护路径认领 agent 的空闲阶段——正是已排期后续轮次所用的同一机制。因轮次正占用 agent 而被拒绝的认领会驻留在 `whenIdle()` 上并在下一个轮次边界重试，同时把待投递批次放回队首，使到达顺序得以保留。投递按会话串行，并合并认领成功时队列中的全部内容，因此一阵突发是一次唤醒携带若干轮次，而不是若干次唤醒。

单条消息的失败被隔离：日志拒绝的消息会被警告并丢弃，其后的队列继续前进。一条无法记录的消息不能让一整段对话沉默。

### 模型可见 ⟺ 已记录，在可能失败的那个方向上

`whatsapp/inbound` 在后续轮次入队**之前**追加，因此日志无法记录的消息永不抵达模型。`whatsapp/outbound` 在 provider 确认发送**之后**追加，因此日志绝不会声称一次被 WhatsApp 拒绝的发送。两者都携带模型可见文本无法反解出的 WhatsApp 身份——对话 id、对话名、消息 id——并且都有 `./invariant` 随附件校验已存记录。

### 发送每次都询问

`whatsapp_send_message` 必填 `chat_id`；没有「回复上一段对话」，没有会话默认值，也不从历史推断，因为一个会话服务多段对话，默认目的地迟早会是错的人。

寻址在这里完全不做校验，在 `listChats()` 中的成员资格也不为它把关。一个真实账号说明了成员资格为何不行：provider 的对话索引以连接为界，因此刚连接的进程确实可能什么对话都不知道，以成员资格把关会恰好在部署重启时让每个工具不可用。两个读取工具都对模型说明了这一点——否则一个空列表会被读成「该账号没有任何对话」，而一段空的历史页会被读成「这段对话是空的」，而不是「这次连接什么都没有保留」，后者会让模型放弃一段它其实仍然可以写入的对话。

校验 id 的*形式*才是薄弱之处，而一个真实账号已经证明了这一点。第一版接受 `@s.whatsapp.net` 与 `@g.us`，并把这一对写成精确的协议常量。WhatsApp 正在推行 `@lid`，即它用于一对一对话的关联身份空间：`whatsapp_list_chats` 返回了一段有名字的 `@lid` 对话，而 `whatsapp_read_chat` 拒绝了自己的列表工具刚刚产出的那个 id，并给出一条断言该取值不是 WhatsApp 地址的消息。后缀是常量；后缀的集合不是。seam 的回应是让 `WhatsAppChatId` 变为不透明，并新增 `ctx.whatsapp.resolveChat()`，于是本包删掉了自己的地址表和 `chatKindOf`，而不是继续扩充它们：现在每个工具都经由账号解析，由账号判定对话的 kind、在本次连接观察过该对话时为其命名，并且只拒绝根本没有指名任何对话的取值。

先解析再做别的，正是让已登出的账号在操作者被要求批准一次发送之前就失败的原因。所接受的代价是：本次连接从未观察过的地址同样能解析出来，因此写错的 id 会走到审批卡片，只有在真正尝试发送时才被拒绝；挡在前面的是卡片中写明的收件人，而对 id 做猜测正是 `@lid` 出错的原因。

未解析出的显示名要如实说明，而不是遮掩过去。第一版上报 `name: chat.name ?? chat.id`，这让每一行渲染都把 id 打印两遍，更糟的是把一串数字呈现给审批的操作者，仿佛它指认了某个人。现在未解析时 `name` 与 `chat_name` 直接缺席，在结果中渲染为 `(unnamed)`，在审批卡片上渲染为 `an unnamed conversation at <id>`，于是「我不知道这是谁」是操作者读到的事实，而不是被伪装成知识的空缺。

审批会先完整指名目的地再引用正文，并在拒绝、取消、通道不可用、组合中没有审批服务，以及没有 agent 的执行这几种情况下一律失败收场。`ctx.approval` 被刻意排除在 `inject` 之外，因此没有审批通道的组合仍会注册只读工具，只拒绝发送。

## 备选方案

**每个账号一个硬编码会话。** 最容易实现，对个人号码也说得通。被否决，因为这个形态是部署的决定而非插件的决定：同时收到群聊流量与客户消息的账号希望用不同的 agent 处理它们，而把两者混在一个会话里会让每次回复都变成一道消歧题。`single` 作为一种路由保留了下来。

**用到达的消息打断当前轮次。** 因为聊天助手理应即时，所以很有诱惑力。被否决，因为轮次是 agent-loop 与会话日志赖以构建的单位：把一条消息插进运行中的轮次，要么破坏正在组装的请求，要么产生无法重放的日志。等一个轮次边界的延迟代价以秒计；另一条路的正确性代价则没有上界。

**每条消息一轮且不做合并。** 作为投递单位被否决，但作为**轮次**单位被保留：一阵六条消息只认领一次空闲阶段，却作为六个轮次进入，因此顺序与每条消息的框架文本得以保留，而 agent 只被唤醒一次。

**自动回复，只对异常发送要求审批。** 直接否决。承担风险的身份是操作者的电话号码，而「异常」不是本包能定义的东西。每次发送都询问；按对话的长期授权推迟给一个可以持久化并可撤销的策略。

**在消费者一侧维护一份 WhatsApp 信封字段名的丢弃清单。** 在一次真实配对的成批消息之后，本里程碑曾一度采用它。当 seam 上报的媒体类型被发现只是最先解码的那个信封键时，此方案被否决：WhatsApp 会在大多数群消息上附带 `senderKeyDistributionMessage`，因此任何宽到足以捕获信令的清单都会丢掉一张发到群里的照片，而这份丢失不会留下任何日志。内容判断属于信封仍然完整的地方。

**一个隐式回复被路由对话的 `reply` 工具。** 在 token 成本上很有吸引力，对 `per-chat` 也相当合适。被否决，因为同一个工具在 `category` 下就是错的，而一个安全性依赖于模型看不见的路由配置的工具是个陷阱。对话 id 已经在模型刚读过的那条消息里了。

**拒绝账号尚未观察到的 chat id。** 最初的设计，而且是错的：它把索引当成名册，而索引只是已观察活动的缓存。一次真实重连为一个拥有大量对话的账号报告了零对话，那样每个工具都会一直失败到有流量到达为止。作为推迟的工作保留：一份跨连接持久化的名册可以让工具区分「不是该账号的对话」与「尚未见过」。

**保留一份消费者侧的 WhatsApp 地址空间表，并把 `@lid` 补进去。** 这是第一次修补，也短暂上线过。在 seam 让对话 id 变为不透明之后被否决：这张表的失效方式恰恰是朝着最糟糕方向的沉默——一段真实对话仅仅因为 WhatsApp 新增了本包没听说过的空间而被拒绝——而这个集合由 WhatsApp 拥有并不断扩充。「在 provider 中把 `@lid` 归一化掉」也曾被提出并谢绝，因为 Baileys 并不总能把一个关联身份映射回电话号码，因此 `@lid` 无论如何都会到达消费者，这张表只会带着一道转换继续存在。provider 已经在每段对话和每条消息上报告 `kind`，因此消费者是在重新推导别人已经交给它的东西。

**对照持久的 `whatsapp/inbound` 日志去重。** 正确，但推迟。内存中的 `seenMessageLimit` 集合覆盖了 seam 真正记录的那种重放（一次进程生命周期内的重连）；在加载时读日志，要为一个只在进程于 provider 重放中途重启时才出现的情况扫描每个会话的全部历史。

## 后果

Web UI 会在仓库工作区旁边显示一个 WhatsApp 工作区，无需任何 UI 改动，因为 `ctx.workspaceRegistry` 已经承载任何带目录的东西。对话会话就是普通会话：它们会压缩、恢复，并可用同一套工具检查。

每条被路由的消息都会到达 LLM 供应商与会话日志。对于私人对话，这是本子系统赖以建立的取舍，在每份 README 中都被重申而不是默认。

`per-chat` 无上限也无淘汰地打开会话；对话很多的账号需要 `allowChatIds` 或分类路由。去重无法挺过重启。二者都记录在各包的「已知限制」中。

配置错误在加载时失败：不可用的目录、拒绝该路径的注册表、打不开的常驻会话、高于 `readChatMaxLimit` 的 `readChatDefaultLimit`。一个悄无声息永远不出现的工作区与一个断线的账号无法区分，而这正是本条排除掉的故障。

## 测试

单元测试与组合测试覆盖了各种路由模式、允许/拒绝的优先级、`fromMe`、重复消息的压制、轮次中途的认领拒绝及其重试、批次合并、会话恢复与目录被移动时的失败、标题固定、每个工具的参数上限与错误字符串，以及每种审批结果。落在陌生地址空间中的 id（其中包括 `@lid`）有一条回归测试，断言它们原样抵达账号。两个 `./invariant` 随附件都针对有效与损坏的已存记录做了演练。一份无密钥快照把已组装的应用完整跑过整套工具，包括一个被账号拒绝的地址、一次操作者拒绝以及一次获批的发送。覆盖率按文件 100%，正如门禁所要求。

**几乎没有任何东西在真实 WhatsApp 账号上验证过。** 每个单元测试都驱动一个脚本化 seam。针对一个已配对账号，对 `dsh-tool-whatsapp` 做过一次真实运行，确实跑通了真实路径——`whatsapp_list_chats`、一次普通发送、一次引用发送、`whatsapp_read_chat`、`whatsapp_mark_read`，以及每次已确认发送恰好一条 `whatsapp/outbound`——因此工具表面在真实 provider 下是站得住的。`dsh-whatsapp-workspace` 未被覆盖，因为路由需要来自第三方而非账号自身的入站消息：工作区及其会话在 Web UI 中如何呈现、队列在一次真实的重连重放下如何表现，仍是本里程碑中最大的未决风险。

那次运行还纠正了本里程碑一直带着的一个假设：连接在刚建立时并不可靠地为空。磁盘上带有 app-state 同步密钥的账号可以在任何消息到达之前就列出会话。没有任何东西依赖索引为空——工具只渲染其中已有的内容——但面向模型的描述不再承诺一个 provider 在任一方向上都不保证的状态。
